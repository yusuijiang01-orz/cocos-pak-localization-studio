# PRODUCT

目标：保留用户熟悉的原版 Studio，同时把翻译过程收敛为可检查的逐文件队列。

必须：不漏玩家可见文本；不提取路径、ID、坐标、脚本和资源字段；按文件翻译；断点续传；raw 结构构建。

编码契约：客户端补丁以 UTF-8 为唯一显示输入。每次物化和构建都将官方 PAK 内全部 TSV、CSV、INI、TXT、LUA 转为严格 UTF-8，包括未翻译原文；禁止按原文件回写 GBK、ANSI、Windows-1258 或 TCVN3。结构修复完成后必须再次 UTF-8 归一化，任何不可解码文件或新增 `U+FFFD` 都阻止打包。

范围定义：玩家展示字段由后台结构分析器判定并持久化；完整导出前会增量重扫，避免旧规则永久漏掉新识别的展示文本。名称、描述、对话、提示及值为自然语言的非结构 INI 字段可进入，配置注释、标识符、路径、资源引用、数值与结构字段不可进入。“展示字段”不等于保证每条废弃数据在当前客户端运行时可达。

本阶段不显示：云 API 审校、国际版迁移、GitHub 发布、旧 CSV 和脚本翻译链路。
## 多 PAK 单表工作流

主工作流支持将项目内全部 PAK 的玩家可见文本合并为一个 XLSX，并在一次导入后同步到各 PAK 的修改目录。完整表采用带外结构骨架，Google 只能看到自然语言片段。汉化率是质量目标与进度指标，不是构建开关；批量构建允许未翻译内容保留原文。

“导入成功”只表示 XLSX 已通过结构校验并安全写回。导入结果必须另外显示剩余越南文记录数；该数字不为零时不得宣称完全汉化。PAK 外的原生库、图片文字或服务器下发文本属于单独来源，不由 PAK XLSX 隐式覆盖。

导入后的“剩余未翻译”分成两个数字：去重片段数代表下一轮真正需要交给 Google 的工作量，资源引用处数代表这些文本在游戏文件中被复用了多少次。Studio 自动在 `remaining_xlsx` 生成残留专用表；该表只含仍有越南文的自然语言，导回时不会覆盖未列出的已有中文。

工具栏同时提供显式“导出未翻译 XLSX”入口，允许用户在任何时候重新扫描并导出当前残留表。它和自动生成的残留表使用同一格式及同一“导入全部 PAK XLSX”入口，不引入第二套导入逻辑。

“按文件 Ollama”同时接受逐文件单 PAK XLSX 文件夹与多 PAK 残留 XLSX 文件夹。后者不依赖当前左侧选中的 PAK；模型写回后使用配套 v7 映射统一导入所有涉及的 PAK，并重新生成下一轮残留表。
